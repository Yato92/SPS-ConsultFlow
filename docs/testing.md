# Тестирование ConsultFlow

Документ описывает стратегию, состав и результаты тестирования решения.

## 1. Подход

| Уровень | Инструмент | Что проверяет |
| --- | --- | --- |
| Модульные | pytest | расчёты стоимости и SLA |
| Интеграционные | pytest + TestClient | API, БД, права, жизненный цикл |
| Проверка типов | `tsc --noEmit` | типы фронтенда |
| Сборка | `vite build` | production-сборка SPA |
| Ручные сценарии | чек-лист | UX, связка бот ↔ дашборд |

Тесты используют отдельную SQLite-базу `tests/consultflow_test.db`, создаваемую на каждый
запуск, детерминированные фикстуры и предсказуемые демо-данные (`random.seed(42)`).

## 2. Запуск

```powershell
# backend
cd backend
..\.venv-backend\Scripts\python.exe -m pytest

# только один модуль
..\.venv-backend\Scripts\python.exe -m pytest tests/test_bot.py -v

# фронтенд
cd ..\frontend
npm run typecheck
npm run build
```

## 5. Ручные сценарии

### Сценарий А. Заявка из Telegram

1. Запустить backend, бота и дашборд.
2. В боте: `/start` → «Оставить заявку» → направление → описание → часы → сложность → подтвердить.
3. Ожидаемо: бот присылает номер, стоимость, срок SLA; менеджеру приходит уведомление.
4. В дашборде: заказ виден в реестре со статусом «Новая заявка», суммой и клиентом.

### Сценарий А2. AI-заявка

1. В VK-боте: `/start` → «✨ AI-заявка».
2. Отправить: «ООО «Вектор», нужен финансовый аудит, 40 часов, сложная задача,
   бюджет 300 000 руб., срок до 20.12.2026».
3. Ожидаемо: бот показывает направление, часы, стоимость, SLA, команду,
   результат проверки дубликатов и черновик КП.
4. Нажать «✅ Создать заявку».
5. Ожидаемо: создаётся заказ с source `vk`; в карточке есть документ
   `proposal` с текстом КП; менеджеру приходит уведомление.
6. Повторить тот же текст: бот предупреждает о похожей заявке.

### Сценарий Б. Воронка и документы

1. Открыть заказ в дашборде.
2. Перевести в «Квалифицирована» → «КП отправлено».
3. Открыть вкладку «Документы»: появилось КП с номером и текстом.
4. Перевести в «Договор подписан» и «Работы выполнены»: появляются договор и акт.
5. Проверить вкладку «История»: все переходы с автором и временем.

### Сценарий В. SLA

1. Найти заказ с прошедшим `sla_due_at` (демо-данные содержат такие).
2. Ожидаемо: красный бейдж с числом дней просрочки, KPI «Просрочено SLA» увеличивается.
3. Перевести заказ в «Закрыт»: просрочка исчезает из активных.

### Сценарий Г. Вход из бота

1. В боте: `/link`.
2. Перейти по ссылке.
3. Ожидаемо: дашборд открывается без ввода пароля, в шапке — имя пользователя.
4. Повторный переход по той же ссылке после истечения 15 минут → предложение войти по паролю.

### Сценарий Д. Права доступа

1. Войти консультантом (`consultant@consultflow.ru`).
2. Ожидаемо: нет кнопок «Новый заказ», «Изменить», «Документ»; доступен просмотр.
3. Войти менеджером: кнопки доступны, смена статуса работает.

### Сценарий Е. Экспорт и фильтры

1. Выбрать статус «В работе» и направление «IT-консалтинг».
2. Нажать «Экспорт CSV».
3. Ожидаемо: файл содержит только отфильтрованные строки, разделитель `;`, кириллица читается.

### Сценарий Ж. Прототип и общая база

1. Открыть <http://127.0.0.1:5173/prototype/> при запущенных backend и frontend.
2. В заявке №104 отправить КП, подписать его в роли клиента, оплатить тестовой
   картой, сформировать договор, начать работу, сформировать и подтвердить акт.
3. Ожидаемо: статус меняется на «Завершена», история, чек и документы сохраняются в БД.
4. Создать заявку в боте от Telegram ID `700000001` — она появляется в прототипе.
5. Сменить статус заявки в прототипе — клиенту создаётся уведомление в боте.

## 6. Проверенные негативные сценарии

| Ситуация | Ожидаемое поведение |
| --- | --- |
| Неверный пароль | `401`, сообщение об ошибке на форме |
| Истёкший/битый токен | редирект на `/login` |
| Недопустимый переход статуса | `400`, сообщение в интерфейсе |
| Чужой заказ в боте | `403` |
| Пустая тема заказа | `422`, подсветка поля |
| Нет соединения с API | карточка ошибки с кнопкой «Повторить» |
| Бот без токена | сервис не стартует и пишет подсказку в лог |

## 7. Ограничения тестирования

- Нет автоматизированных e2e-тестов в браузере (Playwright); UI прототипа проверялся
  вручную и через headless Edge/CDP;
- Telegram проверялся на уровне API и импорта модулей, без реального токена;
- нагрузочное тестирование не проводилось (учебный контур, 76 заказов).
